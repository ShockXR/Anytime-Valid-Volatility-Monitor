## Iteration 1. Calibration windows with MAD = 0 crashed the monitor

**OBJECTIVE.** Make `VolatilityMonitor` and `GaussianLRMonitor` survive calibration windows in which more than half of the returns are exactly zero, or all are missing, without changing any output where the old code worked.

**PROBLEM IDENTIFIED.** Reported by the coordinator from the Nifty work. When more than half of a window's returns are exactly 0 (frozen prices, such as an exchange outage, or coarse price ticks, as for DOGE where the paper's quartiles are both 0), the scaled MAD is 0, so `tau^2 = 0`, `m0 = 0` and `tau^2 / m_dn` raised `ZeroDivisionError`. An all-NaN window gave NaN everywhere and a monitor that silently never alarms. `GaussianLRMonitor` divides by `scale = 0`.

**HYPOTHESIS.** A degenerate window says nothing about the scale of ordinary moves. Waiting for more data fixes a short frozen stretch. For a series whose zero share stays above 50%, waiting never helps, and the scale must come from the nonzero returns. Any positive truncation level keeps the detector valid (`docs/math.md`, 5.2), so a fallback for tau changes power, not validity.

**CHANGES IMPLEMENTED.** In `monitor.py`: a window is usable when `scale > 0`, `tau^2 > 0` and `m0 > 0` (all finite). Otherwise it is extended one return at a time. An extended window is accepted once it is usable and holds at least `cal_len / 2` finite returns (this stops a window of 499 NaN and 1 return from being accepted after an all-NaN stretch). At `cal_max` returns (new keyword, default `2 * cal_len`), the scale falls back to the scaled median of the nonzero absolute returns; with no nonzero return at all, calibration restarts with fresh data. Counts are in `cal_stats` (`calibrations`, `extended`, `fallback`, `restarted`), and per-segment details in `segments`. If the decrease side has no admissible bet (lower baseline 0), its statistic is held at 0, which is a valid e-detector; the old code would have let it count steps and alarm after about 2A steps.

**EXPERIMENTS PERFORMED.** Unit tests in `tests/test_monitor_cs.py`: 60% exact zeros (20,000 steps), a 400-step frozen stretch before ordinary returns, an all-NaN stretch of 1500 steps, a frozen window with a scale floor. Regression: the new classes against a verbatim copy of the old ones on three streams with jumps, NaNs and volatility changes, five configurations (including band, floor, custom grids and the Gaussian monitor), exact equality of every event field, plus values recorded from the old code.

**RESULTS.** All tests pass. With 60% zeros, every calibration is extended to 1000 returns and falls back to the nonzero scale (0.8 to 1.2, true value 1). After the 400-step frozen stretch (cal_len 390), the window reaches the cap of 780 and falls back; the baseline then mixes 400 zeros with 380 normal returns, so m0 is about half the true value and the first segment alarms "up" soon after trading resumes. After an all-NaN stretch, the first calibration uses 250 finite returns.

**IMPROVEMENTS.** No crash and no silent NaN monitor. Default output is bit-for-bit unchanged on every stream where the old code ran.

**REMAINING ISSUES.** A frozen feed is a data problem: zero returns from a stale price are not "zero volatility". Loaders should mark such stretches as missing (NaN). Then the monitor skips them and the up alarm after an outage disappears. This is a change in `data.py`, which E8 does not own.

**NEXT ITERATION.** The confidence-sequence baseline (iteration 2).

## Iteration 2. A confidence sequence for the baseline, and a proof that uses it

**OBJECTIVE.** Make the false alarm guarantee hold when the baseline `m0` is estimated (alternatives A2), with full proofs, and implement it without changing the default monitor.

**PROBLEM IDENTIFIED.** The theorems of `docs/math.md` 5.4 assume the true `m0`. The plug-in has no guarantee, and the one standard error margin (`margin_z`) has none either; its standard error assumes independent observations. A second, quieter problem: `tau` is computed from the same window as `m0`, so the truncated squared returns in the window are not adapted to the information flow, and no martingale argument applies to them directly.

**HYPOTHESIS.** (1) If the increase detector bets against an upper confidence bound U and the decrease detector against a lower bound L that hold uniformly over time with total error δ, then the false alarm probability within m steps is at most δ + m / A. (2) A sample split (tau from the first 25% of the window) restores adaptedness. (3) Time-uniform bounds also allow a data-dependent calibration length.

**CHANGES IMPLEMENTED.**
* `src/avmonitor/confseq.py`: predictable plug-in empirical Bernstein confidence sequence (Waudby-Smith and Ramdas 2024) for a mean in `[0, B]`, vectorised (`eb_confseq`) and streaming (`StreamingEBConfSeq`), with one change: the bet cap uses the one-sided range of the centred variable, which lets the lower bound bet up to about 7 instead of 0.75 for a truncated squared return. `cs_baseline` (sample split), `width_stopping_time`. Numerically stable `psi` (series below 1e-3).
* `monitor.py`: `baseline="cs"`, `delta` (split equally between the two sides), `tau_frac`, `cs_n_plan`, `cs_c`, `target_rel_width` and `cal_max` (adaptive length), `margin_z` for the plug-in. All keyword-only, all defaults reproduce the old behaviour.
* `detectors.calibrate`: keyword-only `baseline="cs"`, `delta`, `tau_frac`.
* `docs/math.md` section 6: Lemma 6.1, Theorem 6.2 (coverage of the bet-weighted average of conditional means, under any dependence), Corollary 6.3, Theorem 6.4 (δ + m / A, and average run length at least (1 - δ) A, for any stopping rule), Corollary 6.5 (constant conditional law), and the three subtle points.

**EXPERIMENTS PERFORMED.** Unit tests: time-uniform coverage at δ = 0.05 on four bounded laws over 2500 paths of 1500 steps, coverage of the weighted average with a deterministic sinusoidal mean, the inequality of Lemma 6.1 on a grid, streaming equals vectorised, width shrinks with n. A first pilot compared the bound with the best possible betting bound for a truncated squared normal return at n = 292; it was then made part of E8 (Q8d, `results/e08d_width_oracle.csv`): oracle upper bound 1.290 times the mean, the empirical Bernstein bound 1.368, a normal-approximation interval 1.189.

**RESULTS.** All coverage tests pass with misses well below δ. The bound is valid but wide for short windows: most of the width is the price of any finite-sample bound for this skewed variable (oracle 1.290), not of this particular construction (1.368). This motivated reporting E8 Q8d.

**IMPROVEMENTS.** A guarantee that covers estimation error, proved in full except for Ville's inequality. The bound is also valid under volatility clustering, where the standard-error margin is not.

**REMAINING ISSUES.** The width at 390 calibration steps is large, so the price in detection delay is expected to be high there (measured in iteration 3). The betting (hedged capital) sequence of Waudby-Smith and Ramdas could close part of the gap to the oracle; not implemented.

**NEXT ITERATION.** Run E8: false alarms, delays, adaptive lengths, width against the oracle, clustering, and the real BTC rerun.

## Iteration 3. Experiment E8: what the proof costs, synthetic and real

**OBJECTIVE.** Measure false alarms, bound failures and detection delays of the plug-in, margin_z = 1 and cs baselines for calibration lengths 390, 1440, 5000 under Gaussian, jump and Student-t5 returns; the adaptive length; the gap to the best possible bound; the choice of δ; clustering; and the real Bitstamp rerun of E5c.

**PROBLEM IDENTIFIED.** E4d suggested the plug-in breaks the bound at 390 steps (5.4% against 5%) from 2000 paths. Whether the cs baseline is worth its price was unknown.

**HYPOTHESIS.** The cs baseline holds its bound everywhere but costs delay, most at short calibration. On real data it should act like a data-driven null band.

**CHANGES IMPLEMENTED.** `experiments/e08_cs_baseline.py` (parts a to g, fixed seeds, chunked to stay under about 1 GB of memory). The first full run had parts a to e. Two questions were added afterwards and run separately, both specified before seeing their results: Q8g (choice of δ, motivated by the conservative rates of Q8a) and Q8f (clustering, to check the claim in `docs/math.md` 6.5 that the i.i.d. standard error has no guarantee there). A control row (plug-in with A = 36,000) was added to Q8e to separate the effect of A from the effect of the baseline. Figures had overlapping log-axis labels and too coarse histogram bins; both fixed.

**EXPERIMENTS PERFORMED.** 10,000 null paths and 2000 change paths per cell (Q8a, Q8b), 5000 paths per adaptive row (Q8c), 500 paths for Q8d, 2000 for Q8g, 4000 GARCH paths for Q8f, nine monitor runs on 264,960 real minutes (Q8e). Total run time about 8 minutes on one core.

**RESULTS.** (all in `docs/report_parts/E8.md`)
* cs keeps the guarantee with a wide margin: at most 0.27% false alarms per day (bound 5%); the confidence bound failed on at most 0.08% of paths (allowed 1%).
* The plug-in at 390 steps is at 4.5% (Gaussian, jumps) and 4.9% (t5) with 10,000 paths, and 5.07% for either side under t5: at the bound, not clearly above it. The E4d excess was within Monte Carlo error. Over 500 steps under t5 it was 7.0% to 7.5% against a 6.4% bound (1 to 2 standard errors).
* Price in delay: 1.8 to 7.6 times the plug-in at 390 steps (first written as 7.2, read off the printed rows; corrected after review round 2a), 1.4 to 3.0 at 1440, 1.2 to 1.7 at 5000. A 25% increase is missed within 2500 steps on 24% to 65% of paths at 390 steps.
* The bound is within 3.5 points of the oracle from 1440 steps on and 7.6 to 10.6 points worse at 390.
* δ between 0.01 and 0.03 gives delays within 5% of each other.
* Under GARCH the cs bound stays valid (0.05% misses at δ = 0.01), the i.i.d.-SE upper bound misses 1.6% at a nominal 1%.
* Real data: cs cuts alarms by 16% to 20% at each band, almost all of them decrease alarms, and raises the decrease hit rate (67% to 82% with no band, 90% to 97% with band 0.25). The larger A alone changes nothing (126 alarms either way).

**IMPROVEMENTS.** The project now has a proved guarantee with an estimated baseline, and a measured price for it. The E4d claim of a broken bound is corrected (not confirmed with 5 times more paths).

**REMAINING ISSUES.** (1) The guarantee is very conservative, so the cs baseline is a poor choice with 390-step calibration unless a proof is required; with 1440 steps or more, or with the adaptive rule, the price is moderate. (2) Under clustering the monitoring null is false whatever the baseline (E9). (3) Not implemented: the hedged-capital betting sequence (could recover at most the gap to the oracle, about 8 to 11 points at 390 steps), a union bound over truncation levels, and a running τ. (4) `docs/experiment_report.md` (not owned by E8) still says E4d found 5.4% against 5%; it should point to E8's re-estimate.

**NEXT ITERATION.** Make the down side cheaper: its bet range depends on τ² / L, so a lower bound that is too low costs twice (a lower null and smaller bets). A separate δ split between the sides (more of δ to the lower bound) could balance the two delays. Not started.

## Iteration 4. Review follow-up: missing returns in the real run, and alarms after recalibration

**OBJECTIVE.** Act on two points of the independent review (round 1) that concern E8: M6 (E5c's line that turns missing returns into zeros was copied into E8) and m5 (the theory covers only the first alarm, while the monitor recalibrates after every alarm).

**PROBLEM IDENTIFIED.** (1) `np.nan_to_num(u, nan=0.0)` makes a missing minute look like a zero return, which is evidence for a volatility decrease. (2) Theorem 6.4 bounds the first false alarm of one segment only.

**HYPOTHESIS.** (1) On the Bitstamp file the change is immaterial (the review found one non-finite value). (2) A "bank" supermartingale over segments plus a per-segment failure budget δ bounds the expected number of false alarms with restarts.

**CHANGES IMPLEMENTED.** `e08_cs_baseline.py` Q8e now passes missing returns through (also to `intraday_scale`). `docs/math.md` Corollary 6.6: with recalibration after every alarm, E[number of alarms within m monitored steps] ≤ (δ + m / A) / (1 - δ); δ = 0 gives the review's m / A for a known baseline. New test `test_recalibration_bound_on_alarm_count`.

**EXPERIMENTS PERFORMED.** Q8e rerun (nine monitor runs). The test runs the cs monitor with A = 100, cal_len = 200 on two i.i.d. streams of 50,000 steps.

**RESULTS.** Q8e: identical alarm counts, directions and hit rates; two medians moved in the fourth decimal (0.8069 to 0.8068, 0.3108 to 0.3106). The test passes with the observed alarm count far below the bound.

**IMPROVEMENTS.** The real run no longer depends on a data-filling choice, and the guarantee now covers the monitor as it actually runs (with restarts).

**REMAINING ISSUES.** `e05_real_btc.py`, `e10` and `cli.py` (not owned by E8) still fill missing returns with 0; harmless on Bitstamp, wrong on Binance and Nifty.

**NEXT ITERATION.** None planned within this session.

## Iteration 5. Missing returns in the cs path, the never-restart rule, and a self-check of the new code and proofs

**OBJECTIVE.** After review round 1, the coordinator asked for three things. First, confirm that the confidence-sequence (cs) path also skips missing returns, and add a test if it did not. Second, check `src/avmonitor/confseq.py` and `docs/math.md` section 6 with the same scrutiny as the review, since the review did not cover them. Third, record commit `002eed7`, made just before the request.

**PROBLEM IDENTIFIED.**
1. No test showed that cs calibration and cs monitoring skip NaN. The existing NaN tests covered the plug-in path and a window that is entirely NaN.
2. Before `002eed7`, the monitor could restart a confidence sequence that had already started, if the second part had too few finite returns. Two sequences at risk in one segment would make the error budget 2δ instead of δ.
3. The self-check found the small issues listed under CHANGES.

**HYPOTHESIS.** Reading the code shows that the cs path skips NaN in three places:
* the τ part keeps only finite returns;
* the sequence part updates only on a finite return;
* `update` returns before it touches the statistics.

A test should confirm this.

**CHANGES IMPLEMENTED.**

*Never restart.* Since `002eed7`, a sequence that has started is never restarted. The monitor keeps collecting returns until the second part has at least half its planned number of finite returns, or until the cap is reached (or longer, while that part has no finite return at all). Each segment therefore uses exactly one sequence (`docs/math.md`, 6.3).

*New test.* `tests/test_monitor_cs.py::test_cs_path_skips_missing_returns` uses 5% missing returns throughout the stream and checks the following.
* τ equals 3 times the scaled MAD of the finite returns in the τ part.
* The segment's bounds equal `eb_confseq` run on the finite values of the sequence part only (to a relative tolerance of 1e-9).
* Filling the gaps with zeros would have lowered the baseline.
* `update(nan)` returns None and leaves both statistics unchanged.
* Up to the first alarm, the run equals a run on the same stream with the missing monitoring returns deleted: same alarm, same mapped index, same statistic.

*Self-check findings (all fixed, each with a test where it is code).*
* The `confseq.py` module docstring cited "Theorem 6.3" for the δ + m / A bound. The correct reference is Theorem 6.4.
* The docstring said the formulas "reduce exactly to theirs". It now says when: their two-sided interval at level α is our pair of bounds with δ_u = δ_l = α / 2 and a = 1.
* A planned size `n_plan` ≤ 0 or NaN gave NaN bets without any error. Both functions now raise an error for it.
* `StreamingEBConfSeq` did not check δ. It now does.
* `width_stopping_time(n_min=0)` blocked every column but the last, because of the slice `:-1`. It now raises an error.
* None of these inputs is used by the e08 script, so no result changes.
* math.md, Theorem 6.4, Step 2: the missing-return step was stated, not derived. It is now derived. Under the missingness assumption of 6.7, E[M_t | F_{t-1}] ≤ M_{t-1} + P(r_t observed | F_{t-1}).
* math.md, Theorem 6.4, Part 2: it now states that it assumes T < ∞.
* math.md, 6.5: the GARCH sentence now names the side (upper 0.05%, lower 0.175% at δ = 0.01 per side) and cites `results/e08f_garch_coverage.csv`.

*Self-check, verified and left unchanged.*
* Lemma 6.1: the integral remainder and the monotonicity of φ.
* Theorem 6.2: the supermartingale step with the one-sided ranges (ẑ - Z ≥ -(1 - ẑ) and Z - ẑ ≥ -ẑ).
* Predictability: the bet, the centre and the variance at step i use data before i only, in both the vectorised and the streaming code.
* The clipping remark.
* Theorem 6.4: Ville's inequality after a random start (Step 3), and optional stopping at bounded times (Part 2).
* Corollary 6.6: the counting argument, #{k : C_k} ≤ 1 + N_m.
* The numbers quoted in section 6:
  * ẑ ≈ 0.11, standard deviation over mean ≈ 1.39, and a range of 6.5 standard deviations, all for a truncated squared normal with c = 3;
  * log 9750 / log 7800 = 1.025;
  * √(4/3) ≈ 1.15;
  * log 2000 / log 100, which gives 29% wider;
  * 0.27% and 0.08%, checked against `results/e08a_null.csv`.

**EXPERIMENTS PERFORMED.** Unit tests only. No e08 part was rerun, because no changed line is on a path the script uses.

**RESULTS.** `python -m pytest -q tests`: 109 passed. One test in `alternatives/risk_switch` failed once during a full run. It is another agent's test file, which was being edited at the time, and it passed when rerun.

**IMPROVEMENTS.** The cs path now has a test showing that a missing return is never treated as a zero. The parameter checks close three silent NaN or masking traps. The proofs now state the two assumptions they used without saying so.

**REMAINING ISSUES.**
1. Review m17: the plug-in branch of `detectors.calibrate` returns NaN when the window holds a NaN, while the cs branch drops NaN. Dropping NaN in the plug-in branch too would change the default output only on inputs where it is NaN today. It is left for the coordinator to approve, because the brief asks for the default behaviour to stay the same.
2. A betting (hedged capital) bound was tried in a scratch pilot. It looks tighter at 390 steps, but it covers only the constant-level null, not the weighted average of Theorem 6.2. It is not implemented, and the pilot numbers are not quoted, because they are not saved under `results/`.

**NEXT ITERATION.** Implement the betting bound for the constant-level case (Corollary 6.3), add it to Q8d, and state its narrower guarantee in section 6.

## Iteration 6. Review round 9 (m5): the Bitstamp loader's filled minutes, and what the fix does to every committed Bitstamp number

**OBJECTIVE.** Measure the effect of the loader fix of review round 9, finding m5 (commit `9e81de1`), on every committed result that reads the Bitstamp BTC/USD file, decide whether to replace the committed results or keep them, and leave every affected script reproducing the committed files exactly.

**PROBLEM IDENTIFIED.** The Bitstamp file fills each minute without a trade with a flat, zero-volume candle that repeats the previous close. Until `9e81de1`, `load_bitstamp_csv` turned each into a zero return, and the next return carried the whole move since the last trade; `docs/math.md` 5.6 forbids zero-filling a missing return. In July to December 2025 that is 782 of 264,960 minutes (0.30%), in 702 runs, the longest 43 minutes [REAL]. The fix makes the returns on both sides of a filled minute missing: 1,485 missing returns instead of 1 [REAL]. The scripts that read the file directly or through E6's `prepare`: E5 (all parts), E6b (the Bitstamp series and the cross-venue check), E7 Q7a (the BTC rows), E8 Q8e, and E19 Part 2 and `blind`; E20's family F5 reads E6's cross-venue file. Nothing in `alternatives/` reads it. A second problem appeared when reproducing: the committed E7 Q7a BTC rows and E8 Q8e were computed with the pooled start of `intraday_scale`, the default until commit `0e7d160` made the profile strictly predictable later the same day, so the current scripts did not reproduce them even with the old loader (Q8e: 147 plug-in alarms at band 0 instead of 156 [REAL]; Q7a: 250,560 deseasonalised BTC returns over 174 days instead of 264,959 over 184 [REAL]).

**HYPOTHESIS.** The fix moves Bitstamp results by amounts small next to their sampling error, but enough to change many printed numbers, because so many of them are cited at two or three digits.

**CHANGES IMPLEMENTED.**
* `avmonitor.data.load_bitstamp_csv` takes `filled="missing"` (default, the fix) or `filled="zero"` (the behaviour before review round 9, documented as kept only to reproduce committed results). Tests: `tests/test_bitstamp_filled_option.py`.
* `e05_real_btc.py`, `e06b_five_coins_monitor.py`, `e07_nifty.py` and `e08_cs_baseline.py` have a module setting `BITSTAMP_FILLED = "zero"` and a command-line option `--bitstamp-filled missing`; `e19_real_null.py` passes the option to E6's `prepare`. `e07_nifty.py` (Q7a, BTC profile) and `e08_cs_baseline.py` (Q8e) pass `start="pooled"` to `intraday_scale` explicitly. The docstrings say why.
* `results/r9_bitstamp_impact.csv`: every committed cell of the affected files that differs in a rerun with `--bitstamp-filled missing` (columns experiment, file, row_key, column, old, new, relative_change; an alarm whose time moved shows as a row present on one side only).
* `results/e07a_daily_iq_nifty.csv` (Nifty only, not affected by m5) replaced by the rerun: the script writes it with six significant digits, the committed file had full precision, and the rerun equals the committed values rounded to six significant digits in every cell.
* A "Review round 9 (m5)" paragraph in the report parts E01_E05, E6, E7, E8, E19 and E20.

**EXPERIMENTS PERFORMED.** Each affected part run twice with the output folder redirected to a scratch folder, once with the scripts' default (`zero`) and once with `missing`: E5 (a, b, c, c_r2), E7 Q7a, E8 Q8e, E6b (all of it, since its random draws run over all series in order), E19 Part 2 (all of it, for the same reason) and `blind`, and E20's `part_holm`. The E19 runs read the E6 outputs of the same mode. Run times with `nice -n 10` and at most 2 worker processes: about 3 minutes each for E6b and E19 Part 2, 5 minutes for `blind`, under 20 seconds for the others.

**RESULTS.**
* Reproduction: with the default (`zero`) every result CSV of these parts is byte-identical to the committed file (30 files, E20's `e20_holm_existing.csv` included) [REAL].
* Effect of the fix (`results/r9_bitstamp_impact.csv`, all [REAL]): zero returns 5.4% instead of 5.7%; E5c band 0.25, 129 alarms (74 up, 54 down) instead of 126 (73, 52), validated 80% and 91% instead of 81% and 90%; E5c round 2 band 0.25 unchanged (126; 81%, 90%); Q5b over 174 days instead of 184 (10 days fall below 1,400 returns); E6 Bitstamp band 0.25 unchanged in counts and shares; cross-venue band 0.25, 72% and 72% instead of 72% and 73%, p-values unchanged; Q8e, the cs baseline cuts alarms by 17% to 22% instead of 16% to 20% (cs 129, 100, 71 against plug-in 156, 125, 91); E19 Bitstamp cs counts 131, 100, 71 instead of 132, 101, 76. The largest changes are in the Gaussian LR benchmark: its E5c round 2 decrease alarms fall from 45 to 37 and its cross-venue share from 60% to 51%.
* The fix changes far more than 25 cited numbers (more than 40 in the E5 section alone, and about 50 cells of the Q8e table), so the committed results are kept (option b of the request), with the effect documented in each report part.

**IMPROVEMENTS.** Every Bitstamp result is reproducible again by the scripts as they stand, including E7 Q7a and E8 Q8e, which had silently stopped reproducing when the profile default changed. The size of the m5 effect is on record cell by cell.

**REMAINING ISSUES.**
1. The committed Bitstamp numbers use zero-filled minutes, against `docs/math.md` 5.6; the effect is small and documented, but a future full rerun should switch the scripts to `missing` and update the report parts and the paper together.
2. E7 Q7a and E8 Q8e keep the pooled profile start, which uses up to 20 days of future data in their first days; E5c round 2 and E6 show the past-only profile with a warm-up.
3. The choice to keep the committed results was made after seeing the effect (post hoc), by the rule set in the request (replace only if about 25 or fewer cited numbers change).

**NEXT ITERATION.** None planned; switching the Bitstamp scripts to `missing` belongs to the next full rerun of the real-data results.
